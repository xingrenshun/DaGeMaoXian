## TTSDK 构建报错「Failed to activate emscripten glx」复发 —— 已彻底修复

### 现象
9-21 已把 `Assets/Editor/StarkBuilderSetting.asset` 的 `enableEmscriptenGlx` 改成 `0`，
并且成功构建过一轮（拿到 `Total compressed size 4.9 MB`）。今天再构建又报同样的错
（16:12:46 / 16:13:06 各一次），且设置文件里该字段**又变回了 1**。

### 根因（Editor.log 铁证）

```
16:13:05  Start importing Assets/Editor/StarkBuilderSetting.asset ...
16:13:05  build begin, workspace: ...\tt-minigame
16:13:06  Disable EmscriptenGLX importer path: ...libemscriptenglx_3_1_39.a
16:13:06  Disable EmscriptenGLX importer path: ...libemscriptenglx.a
16:13:06  Disable EmscriptenGLX importer path: ...libemscriptenglx_2021.a
16:13:06  EmscriptenGLX plugin not supported for current Unity version
16:13:06  Exception: Failed to activate emscripten glx
```

**`Start importing` 紧贴 `build begin`** ⇒ 是 **TTSDK 工具在每次点构建时，先把自己内存里的
StarkBuilderSettings 重新落盘一遍**，这一步把 `enableEmscriptenGlx` 从 0 带回 1，
时间点正好夹在「我们的校验之后、构建读取之前」。所以**改一次文件必然复发**。

`AutoFix` 的自证：日志第 82 行命中「构建设置已是正确值，无需改动（自动）」分支，
说明它启动时读到的确实是 0 —— 修改本身没白做，是被工具覆盖了。

**另一个重要发现**：翻遍 `ttsdk_tools.dll` 与 `com.bytedance.ttsdk.base-editor.dll` 的界面字面量，
**TTSDK 工具窗口根本没有暴露 GLX 勾选框**。该字段由工具内部逻辑维护，用户手动改不了 → 只能代码拦截。
（这推翻了 9-21 记的「改完要关掉重开工具窗口」这条不够——重开也没用，构建设置面板里没这个选项。）

### 修复：`Assets/MyAssets/Editor/RopeTTSDKBuildFix.cs` 升级为四层守卫

| 层 | 时机 | 实现 |
|---|---|---|
| L1 | 编辑器启动 / 域重载 | `RopeTTSDKBuildFix.AutoFix`（原有） |
| L2 | asset 保存**之前** | **新增** `RopeTTSDKSettingsSaveGuard : AssetModificationProcessor.OnWillSaveAssets` |
| L3 | asset 导入**之后** | **新增** `RopeTTSDKSettingsGuard : AssetPostprocessor.OnPostprocessAllAssets` |
| L4 | 编辑器每秒 | **新增** `RopeTTSDKBuildFix.Watch`（`EditorApplication.update`，1s 节流） |
| L5 | 构建开始前 | `RopeBuildPreflight`（原有，管 WebGL 模板） |

**L3 是决定性的一层**：工具构建走
`TTSDK.Tool.StarkSDKToolWindow:BuildByNewTool(StarkBuilderSettings settings)` ——
**直接把内存实例传进构建流程**，所以在 asset 刚落盘的那一刻改这个实例，它读到的就是 0。

实现要点（下次改这段代码别踩）：
- 改字段用**反射**（兼容 bool/int，`while (t != null)` 向上遍历基类），
  **不用 SerializedObject** —— 在 `OnPostprocessAllAssets` 里调 `ApplyModifiedProperties` 会重入；
- postprocess 里**绝不调 `AssetDatabase.SaveAssets()`**（递归），落盘交给 `EditorApplication.delayCall`；
- `AssetModificationProcessor.OnWillSaveAssets` **必须原样 `return paths`**，否则保存被静默阻止；
  且该路径下调 `ForceMemoryInstance(markDirty: false)`，避免「保存完又变脏」死循环；
- `Watch` / `ScheduleSave` 都要跳过 `BuildPipeline.isBuildingPlayer`（打包中不动设置）。

### 产出
- 备份：`_RopeGlxGuard_Backup_20260922_161543\StarkBuilderSetting.asset`
- 报告：`_GLX构建报错复发修复报告.html`

### 待用户验证
切回 Unity 等重编译 → **直接点构建，不需要改任何设置**。
成功标志：构建日志不再出现 `Disable EmscriptenGLX importer path`；
Console 若出现 `[TTSDK构建修复] 保存前拦截…` / `拦截到…改回了 1` 是**守卫生效的证据，不是报错**。

## 抖音激励广告报「The AdUnitId is invalid (1002)」—— 自举抢跑顶掉场景配置

### 现象
真机调试点激励视频，报 `The AdUnitId is invalid` / errorCode 1002。
报出的 adUnitId 是 `f32bf9970ah83mqlkg`，而用户提供的激励视频 ID 是 `3hdbhgb64i2642k0j6` —— **对不上**。

### 根因：工程里同时存在三份广告配置，生效顺序反直觉

| 来源 | 配置内容 | 结局 |
|---|---|---|
| `main.unity` 场景里的 AdManager 组件 | AppId 空、激励 `3hdbhgb64i2642k0j6`、插屏 `76srha9mdks28qhemc` | **被销毁** |
| `TikTokAdBootstrap.cs` 自举创建的实例 | AppId 空、两个列表都空 | 活下来，但什么都没配 |
| `AdManager.GetRandVideoAdId()` 写死的默认值 | `f32bf9970ah83mq1kg` / 插屏 `dk217ga5e5b48uo4gh` | **最终生效** |

链条：`TikTokAdBootstrap.Init()` 原先用 **`BeforeSceneLoad`** → 抢在场景 Awake 之前占住 `AdManager.Instance`
→ main 场景里配好的那个 AdManager 按单例写法 `Destroy(gameObject)` 自我销毁
→ 活下来的实例列表为空 → `GetRandVideoAdId()` 回退到写死的、**不属于本 App** 的废弃广告位 → 抖音回 1002。

⚠ **这正是技能 `unity-douyin-rewarded-ad-migration` 早已写明的规则**：
「自举必须用 AfterSceneLoad，不能用 BeforeSceneLoad」。本工程恰好踩在同一条线上。

### 修复
1. **`TikTokAdBootstrap.cs`**：`BeforeSceneLoad` → **`AfterSceneLoad`**；逻辑改为
   「场景里有 AdManager 就**只补空字段**（尤其 AppId）、绝不覆盖已填的值；场景没有才自建并写兜底配置」。
2. **`AdManager.cs`**：删掉两处写死的废弃广告位 ID → 改成 `LogError` + `return string.Empty`；
   两条"将使用默认广告位"的误导性 LogWarning 一并改 LogError。
   ⚠ 该文件有 **110 个历史损坏的 U+FFFD 替换字符**，用 Python 精确替换并断言数量不变（110 → 110 ✓）。
3. **`TikTokPlatform.cs`**：激励/插屏创建前判空 ID（避免把空串丢给 SDK 后卡死在 `timeScale=0`）；
   广告位 ID 变化时重建实例；`AppId` 为空时回退 `TikTokAdBootstrap.AppId`；
   把误导性的 `if (!miniAppid.EndsWith("07"))` 改成 `StartWith("tt")` 检查
   （用户 appid `tt9bb6ed0b05ce27b002` 完全合法，原来每次启动都误报"抖音APPID格式错误"）。

### 关键判据（30 秒定位，已写进技能）
**把报错里的 adUnitId 和工程里配置的 ID 对一下**。对不上 = 生效的不是你配的那份 →
直接查自举时序和写死的默认值，**不要**去抖音后台查广告位审核状态。
⚠ 报错里的 `l` 与源码里的 `1` 极易看混（`...mqlkg` vs `...mq1kg`），grep 时两种都带上。

### 产出
- 备份：`_RopeAdFix_Backup_20260922_163142\`（3 个 .cs + main.unity）
- 报告：`_广告ID无效报错修复报告.html`

## 18:53 「点下一关就卡死」——DOTween 补间活过场景销毁 + 异常支持 None

### 现象
通关后点「下一关」，抖音开发者工具里整局冻死。Console 只有 `Uncaught exception from main loop` /
`Uncaught:` / `Halting program` / `[TMG][AppLog-error] errorCode 2001` / `[TMC][USER_RUNTIME_ERROR] at rAF callback`，
Unity 侧一条可读报错都没有。

### 排查过程中排除掉的（别再重复走）
- **不是广告问题**：Console 里 `插播广告关闭` + `小游戏:…没点击事件埋点` 都正常打印了，
  说明 `TikTokPlatform` 的 `interAdIns.OnClose` 回调**完整跑到底**（`没点击事件埋点` 是 `SendGameAddiction()` 第 383 行打的）。
- **不是关卡越界**：`MyAssets/Levels/` 840 个 json ↔ `Gameplay.unity` 的 `levelsJson` 840 条，索引 0–839 完全对齐；
  且 `InvokeWinGame()` 在 `levelNo >= 839` 时走的是「敬请期待」面板，点不到「下一关」。
- **不是内存**：没有 OOM / `Cannot enlarge memory arrays` 字样。
- 跑的是**当天 18:46 构建成功的新包**（GLX/模板问题已解决），产物在 `tt-minigame/tt-minigame/`。

### 决定性证据：用 webgl.symbols.json 把 wasm 栈翻回 C#
构建产物里的 `webgl.symbols.json` 是 121879 条 `{"函数索引":"符号名"}` 扁平映射。
把 Console 里崩溃栈的函数号喂进去：

| wasm 函数 | 符号 |
|---|---|
| `[32164]` | `List<T>.BinarySearch`（泛型共享槽，名字仅供参考） |
| `[37521]` | `ShortcutExtensions_DOColor`（DOTween） |
| `[37677]` | `U3CU3Ec__DisplayClass44_0_U3CDOScaleU3Eb__1` = **DOScale 的 setter 闭包** |
| `[59201]` | **`Transform_set_localScale`** ← 崩溃点 |
| 最外层 | `invoke_viiiiiiiiiiii`（JS 反调进 wasm） |

→ 崩溃发生在 **DOTween 补间执行 `transform.localScale = 值`** 那一刻。

### 根因链
1. 通关瞬间多条补间在跑：`winPanel.DOScale(.5f)`、`CoinsAnimation` 每枚金币 4 条带 `SetDelay(delay+1.5f)`
   （最后一枚要到**通关后约 2.7 秒**才结束）、`Roll.RotateRoll()` 的 `DORotate(...).SetLoops(-1)`（**永不结束**）。
2. 玩家此时点「下一关」→ `SceneManager.LoadScene("Gameplay")` → 场景物体全销毁，**补间还活在 DOTween 全局列表里**。
3. 下一帧补间继续更新 → 给已销毁 Transform 写 `localScale` → `MissingReferenceException`。
4. 本工程 `ProjectSettings.asset` 的 **`webGLExceptionSupport: 0`（Enable Exceptions = None）**
   → WebGL 编译成 `DISABLE_EXCEPTION_CATCHING`，**任何托管异常都无法捕获，直接 abort 整个 WASM**
   → `Halting program`、整局卡死，且 `try/catch`（含 DOTween safeMode）一并失效。

### 修复
1. **新增 `Scripts/RopeSceneGuard.cs`**（统一跳转入口）：`Load(string)` / `Load(int)` / `ReloadCurrent()`，
   跳转前 `DOTween.KillAll()` + `Time.timeScale = 1f`。文件顶部写全根因，防止后人再裸调 `LoadScene`。
2. **`GameManager.cs`**：8 处裸 `LoadScene` 全部改走守卫；两个通关面板 `DOScale` 加 `.SetLink(面板)`；
   补 `AudioManager`/`CoinsManager`/`Toast` 空判断。
3. **`CoinsAnimation.cs`**：4 条补间全加 `.SetLink(coin.gameObject)`（延迟最长，触发概率最高）。
4. **`Roll.cs`**：`RotateRoll()` 无限循环补间加 `.SetLink(gameObject)`。
5. **`IAPShopManager.cs` / `MainMenuController.cs`**：跳转改走守卫。
6. **`AdsManager.cs`**：新增静态 `TryShowInterstitial()`（空安全）；`ShowRewardVideo()` 也补空判断。
7. **打开 WebGL 异常支持**：`ProjectSettings.asset` 的 `webGLExceptionSupport` `0` → **`2`**
   （FullWithoutStacktrace），并在 `Editor/RopeTTSDKBuildFix.cs` 的 `RopeBuildPreflight.OnPreprocessBuild`
   里加构建前强制（TTSDK 的 `SetupWebGLBuildSettings` 会覆盖 PlayerSettings，该回调晚于它，最终生效的是我们的值）。
   → 以后异常只打日志、游戏继续跑。代价包体 +几百 KB。

### 验证方式
通关后**在两三秒内立刻点「下一关」**（原来 100% 崩的时序），应正常进下一关；
Console 不再出现 `Halting program`。

所以 `tt8474f2c91a0fb1c002` **不是模板残留**。appid 影响构建/上传归属，未擅自改。
