抖音激励广告「AdUnitId is invalid」排查修复报告

宥如极速冒险（打个毛线 Rope）· TTSDK 6.9.4 · 真机调试 · 2026-09-22
根因已定位 三处来源已归一 不是广告位的问题
一句话结论
不是广告位 ID 填错了。你在 main 场景里配的那个 ID，从头到尾就没生效过。
自动初始化器抢在场景加载之前创建了一个空配置的 AdManager，把场景里配置好的那个实例顶掉了； 于是列表为空，代码回退到一个写死的、不属于本 App 的废弃广告位，抖音自然回 1002。

一、报错与突破口

state: {"error":"adUnitId: f32bf9970ah83mqlkg", ... ,"errorCode":1002,"data":...}
ERROR [JS/RewardedVideoAd]: OnRewardedVideoAdStateChanged: error, adUnitId: f32bf9970ah83mqlkg, code: 1002, msg: The AdUnitId is invalid
ERROR [JS/StarVideoAd]: lexacy showWithResult reject, adUnitId: f32bf9970ah83mqlkg, err: {"errCode":1002,"errMsg":"The AdUnitId is invalid"}
突破口就在这一行：你告诉我的激励视频 ID 是 3hdbhgb64i2642k0j6，而报错里的 adUnitId 是 f32bf9970ah83mqlkg —— 两者完全对不上。
这说明「运行时代码手里拿的广告位」根本不是你以为的那个，连去抖音后台查广告位审核状态这一步都该跳过。

三、根因时序

1
BeforeSceneLoad：自举抢先创建 AdManager
TikTokAdBootstrap.Init() 跑在场景加载之前，创建一个空壳 AdManager（AppId 空、两个广告位列表都空），并占住 AdManager.Instance。
2
场景加载：配好的那份把自己销毁了
main.unity 里的 AdManager Awake() 时发现 Instance != null，按单例写法执行 Destroy(gameObject) —— 你精心配的 3hdbhgb64i2642k0j6 就这样一起被丢掉了。
3
Start：列表为空 → 回退到写死的废弃 ID
GetRandVideoAdId() 发现 videoAdIdList.Count == 0， 只打了一条 LogWarning 就 return "f32bf9970ah83mq1kg" —— 一个从别的工程带过来的、跟本 App 毫无关系的广告位。
4
点广告 → 抖音回 1002
TT.CreateRewardedVideoAd 拿着这个陌生 ID 去请求， 抖音当然说 The AdUnitId is invalid。

四、修复内容

1. TikTokAdBootstrap.cs：把自举时机从 BeforeSceneLoad 改成 AfterSceneLoad

这是最关键的一改。
AfterSceneLoad 时场景对象的 Awake() 已经执行（Instance 已就位）， 但 Start() 还没执行 —— 正好是补配置的窗口期。现在的逻辑变成：
  • 场景里有 AdManager → 尊重它的配置，只补齐它空着的字段（尤其是 AppId），绝不覆盖已填的值；
  • 场景里没有 AdManager（例如直接进 Gameplay / CoinShop）→ 才自建一个，写入脚本里的兜底配置。
这样「在 Inspector 里配好了却不生效」这种反直觉的坑就彻底消失了。

2. AdManager.cs：删掉两个写死的废弃广告位 ID

// 改前：列表为空时静默使用一个不属于本 App 的 ID —— 这是把 1002 的排查方向
// 牢牢带偏的元凶
if (videoAdIdList.Count == 0) return "f32bf9970ah83mq1kg";

// 改后：空就是空，报明确的错，并告诉你该去哪配
if (videoAdIdList.Count == 0)
{
    Debug.LogError("[广告] videoAdIdList 为空！请到 TikTokAdBootstrap.cs 的 VideoAdIds 里配置");
    return string.Empty;
}

插屏那条 dk217ga5e5b48uo4gh 同样处理。另外把 Start() 里"将使用默认广告位"这两条误导性提示也改成了 LogError + 明确的指引。

3. TikTokPlatform.cs：加空值保护、修掉误导性校验

  • 空 ID 直接拦下：CreateRewardedVideoAd / CreateInterstitialAd 在 ID 为空时不再调 TT 接口，而是给出一句能看懂的中文错误。避免把空字符串丢给 SDK、 卡在 timeScale = 0 上等一个永远不来的回调。
  • 广告位 ID 变化时重建实例：原实现只在 rewardedVideoAd == null 时重建， 换了 ID 也不会生效，属于隐藏隐患。
  • 修掉一处误导性校验：if (!miniAppid.EndsWith("07")) 会给你那个完全合法的 appid tt9bb6ed0b05ce27b002 每次启动都误报"抖音APPID格式错误"， 已改成按抖音规则检查 tt 前缀。
  • AppId 兜底：万一自举补 AppId 的时机出现意外，回退到脚本里的常量，避免埋点带空 appid。

五、修好之后的表现

真机启动后，日志会明确告诉你用的是哪份配置：
  • [广告] 场景中的 AdManager 有 1 项为空，已用 TikTokAdBootstrap 的兜底值补齐（已填的值保持不变） —— 正常情况，只补了空的 AppId；
  • 点激励视频时，请求的 adUnitId 应该变成 3hdbhgb64i2642k0j6，不再出现 1002。

六、还需要你留意

  1. 广告位必须已审核通过：抖音后台新建的广告位在审核通过前调用同样会失败。 如果改完之后仍报 1002，那就真的是广告位状态的问题了 —— 这一步现在才值得去后台查。
  2. 必须在真机上验证：开发者工具的广告填充率极低，容易出现"加载不到广告"的假象， 不要把工具里的结果当成结论。
  3. 以后改广告位 ID 改哪里： 两个地方都有效 —— 场景里 AdManager 组件的 Inspector，或 TikTokAdBootstrap.cs 的常量。 现在场景优先，脚本常量只作为「场景里没挂 AdManager」时的兜底。
  4. AppId 已一并填入 tt9bb6ed0b05ce27b002（场景里原本是空的，由脚本补上）。
