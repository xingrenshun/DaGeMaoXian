「点下一关就卡死」排查修复报告

工程：宥如极速冒险（ColorRope / 打个毛线 Rope）　·　Unity 6000.2.15f1 + TTSDK 6.9.4　·　2026-09-22
一句话结论：不是广告的问题，也不是场景跳转逻辑的问题 —— 是 DOTween 补间在场景被销毁后仍然去写已销毁物体的 Transform，抛出 MissingReferenceException；而本工程 WebGL 的 Enable Exceptions = None，这个异常无法被捕获，直接把整个 WASM abort 掉，于是整局游戏卡死、Unity 侧连一条可读报错都没有。

1. 现象

在抖音开发者工具里通关后点「下一关」，游戏直接冻死。控制台只有这么几条： 
✖ Uncaught exception from main loop:   tmg-core.js:1
   at wasm://wasm/9c6e38c2:wasm-function[59201]:0x1a93ec9
   at wasm://wasm/9c6e38c2:wasm-function[37677]:0xc7cd385
   at wasm://wasm/9c6e38c2:wasm-function[37521]:0xc9cd59b
   at wasm://wasm/9c6e38c2:wasm-function[32164]:0x8c2b96
   at invoke_viiiiiiiiiiii (webgl.framework.js:10:501466)
✖ Uncaught:

后面跟着的 插播广告关闭 / 小游戏:tt9bb6ed0b05ce27b002没点击事件埋点 是正常的广告回调日志，不是崩因 —— 说明广告那条链路已经完整跑完了。

2. 关键证据：把 wasm 栈翻译回 C#

构建产物里带了 tt-minigame/tt-minigame/webgl.symbols.json（121879 条 函数索引 → 符号名 映射）。把崩溃栈里的函数号直接喂进去：
wasm 函数符号名含义
invoke_viiiiiiiiiiii(webgl.framework.js)JS 反向调进 wasm 的桥接入口
[32164]List<T>.BinarySearch泛型共享槽，名字仅供参考
[37521]ShortcutExtensions_DOColorDOTween 的 DO* 扩展方法族
[37677]…DisplayClass44_0_<DOScale>b__1DOTween DOScale 的 setter 闭包
[59201]Transform_set_localScale崩溃点：给 Transform 写 localScale
结论：崩溃发生在「DOTween 的补间执行到 transform.localScale = 值」这一瞬间。 而不是在广告回调里、不是在 JSON 解析里、也不是关卡越界（已核对：840 个关卡文件 ↔ 场景 levelsJson 列表 840 条，索引 0–839 完全对齐，且最后一关走的是「敬请期待」面板，点不到「下一关」）。

3. 根因链（5 步）

① 通关瞬间，一堆补间同时在跑：
    GameManager.InvokeWinGame() → winPanel.transform.DOScale(one, .5f)
    CoinsAnimation.CountCoins() → 每枚金币 4 条补间，带 SetDelay(delay+1.5f)，最后一枚要到通关后约 2.7 秒才结束
    Roll.RotateRoll() → DORotate(...).SetLoops(-1)，无限循环、永远不会自己结束

② 玩家在这期间点「下一关」→ SceneManager.LoadScene("Gameplay")

③ 场景被销毁，winPanel / 金币 / Roll 这些物体全没了，但补间还挂在 DOTween 的全局列表里

④ 下一帧 DOTween 继续更新 → 对已销毁的 Transform 写 localScale → MissingReferenceException

⑤ 本工程 webGLExceptionSupport: 0（Enable Exceptions = None） → WebGL 里编译成 DISABLE_EXCEPTION_CATCHING，任何托管异常都无法捕获，直接 abort 整个 WASM → 表现就是 Uncaught exception from main loop / Halting program / 整局卡死。
为什么以前没人发现？同类问题在编辑器里只会打一条红字、游戏照跑；在真机上却会死得干干净净。
而且 None 这一档连代码里的 try/catch 都是失效的（DOTween 自己的 safeMode 也就救不回来），所以现场一点可读线索都不留 —— 这也是这次必须靠 webgl.symbols.json 反查的原因。

4. 修复清单

① 根因修复：切场景前统一回收补间

文件改动
Scripts/RopeSceneGuard.cs
新建		 新增场景跳转统一入口 Load(string) / Load(int) / ReloadCurrent()， 跳转前先 DOTween.KillAll() 并恢复 Time.timeScale = 1。 文件顶部写了完整的根因说明，以后谁再想在跳转前直接 LoadScene 会先看到这段。
Scripts/GameManager.cs 8 处裸 SceneManager.LoadScene 全部改走守卫（下一关、重开、主页、OpenScene、两个调试键）；
两个通关面板的 DOScale 加 .SetLink(面板)（面板被销毁时补间自动回收）；
补上 AudioManager / AdsManager / CoinsManager / Toast 的单例空判断。
Scripts/CoinsAnimation.cs 金币的 4 条补间全部加 .SetLink(coin.gameObject) —— 这是触发概率最高的一处（延迟最长、最容易在还没跑完时切场景）。
Scripts/Roll.cs RotateRoll() 的无限循环 DORotate 加 .SetLink(gameObject) —— 它永远不会自己结束，只要关卡在它转着的时候被销毁就必崩。
Scripts/IAPShopManager.cs
Scripts/MainMenuController.cs		 各自那处跳转改走守卫，广告调用换成空安全的 AdsManager.TryShowInterstitial()。
Scripts/AdsManager.cs 新增静态方法 TryShowInterstitial()：Instance 未就绪时静默跳过，不再让 AdsManager.Instance.XXX 抛空引用。

② 第二层保险：打开 WebGL 异常支持

把 webGLExceptionSupport 从 0（None）改成 2（Full Without Stacktrace）：
  • ProjectSettings/ProjectSettings.asset 已改；
  • 同时在 Editor/RopeTTSDKBuildFix.cs 的 RopeBuildPreflight.OnPreprocessBuild 里加了构建前强制校验 —— 因为 TTSDK 的 SetupWebGLBuildSettings 会在构建时覆盖 PlayerSettings，而这个回调的时机晚于它，最终生效的是我们的值。
作用：以后再出现空引用/索引越界，是「一条红字日志 + 游戏继续跑」，而不是「整局游戏没了」。
代价：包体增加约几百 KB、性能略降。当前包体 16MB 左右，离 30MB 还有余量。
这是独立的第二层保险，不是根因修复。即使不改这一项，上面的补间修复也已经能解决问题； 但如果哪天又冒出新的异常，有这一层你不会再看到「整个游戏卡死」这种不可诊断的现场。

5. 怎么验证

  1. 切回 Unity，等编译完成，Console 不应有红色 error。
  2. 直接点构建（不用改任何设置）。
  3. 开发者工具里跑到通关 → 在通关面板刚弹出的两三秒内立刻点「下一关」 —— 这是原来 100% 崩的时序，现在应当正常进入下一关。
  4. 重复几次通关/重开/进商店/回主页，确认都不再出现 Halting program。
成功标志：控制台里再也不会出现 Uncaught exception from main loop 与 Halting program。

6. 顺带发现的一个独立问题（未改，等你确认）

构建 appid 与广告 appid 不一致：
位置值
Assets/Editor/StarkBuilderSetting.asset 的 _appId
（会被写进构建产物的 project.config.json）		tt8474f2c91a0fb1c002
广告 SDK 的 AppId（TikTokAdBootstrap.AppId，你给我的）tt9bb6ed0b05ce27b002
对照本机其它 7 个同类工程，每个工程的 _appId 都各不相同（tt52a5… / ttd97a… / tt8e7c… / tt6c0b… / tt2951… / tt9e71…）， 所以 tt8474f2c91a0fb1c002 不是模板残留，是本工程构建窗口里填着的值。两个 appid 指向不同的应用， 而广告位只对「所属的那个应用」有效 —— 真机上广告能不能填充，取决于运行 appid 与广告位归属是否一致。

我没有擅自改它，因为 appid 会直接影响构建/上传归属。请确认一下：这个包到底应该跑在哪个 appid 下？ 如果就是 tt9bb6ed0b05ce27b002，把 StarkBuilderSetting.asset 里的 _appId 换成它即可（一行）。
